# 渐进训练流程修复、性能与效果验证

## 1. 结论摘要

本轮工作的主要收益不是让纯几何优化从约 2.4 秒/影像继续变快，而是消除在线语义、视频渲染、重复评估和无效输出造成的额外等待，使完整训练流程更稳定、更可解释。

在相同 Phantom3 stage 14–414 全量配置下：

- 纯几何训练平均耗时从 2.791 秒/影像变为 2.823 秒/影像，慢 1.13%，可视为基本持平而非提升；
- 若以曾使用的 2.4 秒/影像为参照，完整场景平均值 2.823 秒反而慢 17.62%；
- 包含在线语义同步和训练视频的端到端耗时从 3.963 秒/影像降到 3.179 秒/影像，减少 19.80%；
- `ProgressiveEndToEnd` 从 1585.291 秒降到 1271.417 秒，减少 313.875 秒；
- 整次运行墙钟时间从 2374.792 秒降到 2014.231 秒，减少 15.18%。

因此，“训练流程吞吐有明显提升”是成立的；“每张影像的纯几何训练速度超过原来的 2.4 秒基线”并不成立。早期 stage 14–18 小范围运行可达到约 2.23–2.26 秒/影像，是因为此时只有约 32 万 Gaussian，不能与增长到约 68 万 Gaussian 的全量平均值直接比较。

最终 RGB 训练指标有一致但很小的改善，不能据此声称算法质量显著提高。最终 Semantic TDOM 保持 `exact_final`，但当前没有独立语义真值指标，因此只能确认完整性和一致性，不能声称语义精度提高。

## 2. 修复前训练代码与流程的问题

### 2.1 在线语义存在随历史增长的长尾

旧逻辑把数值编号较小但较晚出现的影像当作乱序数据，并在每次出现时重新投影全部历史标签。Phantom3 stage 134–138 连续引入 `000111..000115` 时，每个阶段的语义等待达到 56–58 秒，而对应 RGB 和 Semantic TDOM 光栅化本身均不到 0.12 秒。

在线语义本来就是用于实时展示的有界近似；为了暂时维持精确历史顺序而反复执行 O(history) 重建，违反了在线流程的成本边界。现在晚到观测直接融合到当前状态，并诚实标记 `historical_evidence_stale` / `stale_online`。最终冻结几何后仍从全部有效标签执行一次权威 `exact_final` 重建。

优化后，完整运行中 118 个视频采样边界的语义等待平均 0.733 秒、最大 1.409 秒，不再出现数十秒长尾。

### 2.2 大图视频渲染存在显存峰值和 OOM 风险

旧训练视频先整幅渲染 RGB TDOM。大范围 Gaussian–tile binning 会产生较大的 CUDA 临时工作集；RGB 图已经复制到 CPU 后，allocator 中仍保留缓存，紧随其后的 Semantic TDOM 容量检查可能无法保留 512 MiB 安全余量。

修复后：

- RGB TDOM 使用保持全局投影和深度顺序不变的精确分条 renderer；
- 每条 RGB 结果立即复制到 CPU；
- RGB 与语义渲染之间释放可回收 CUDA cache；
- Semantic TDOM 继续按指定 tile rows 分块，并在容量判断前后释放临时缓存。

完整 Phantom3 运行没有发生 OOM。阶段记录的 CUDA peak allocated 最大约 2.90 GiB，peak reserved 最大约 9.39 GiB。

### 2.3 冷启动输入不完整时会进入训练后才失败

使用 `persistent_union` 时，中间 stage 的本地 COLMAP snapshot 可能只包含当前 overlap 子集，而不包含累计历史。例如 stage 120 累计身份集合有 120 个相机，本地 snapshot 只有 23 个。旧流程继续进入 CUDA，最终表现为异步索引越界。

现在 preflight 在训练前检查无恢复点冷启动的初始 snapshot 是否覆盖完整累计身份集合。不完整时立即报告缺失身份，并要求从完整锚点开始或提供兼容 recovery checkpoint。

### 2.4 最终状态、评估和计时存在逻辑错误

修复内容包括：

- 视频末帧已经使用 exact-final 像素时，不再被异步状态查询重新标记为 `approx_online`；
- 最终相机 PSNR 使用每台相机的 `Tri_Mask`，排除去畸变后的无效像素；
- 可见 Gaussian 数从错误的布尔张量长度改为 `count_nonzero`；
- 最终指标计算、逐相机 CSV 和 JPEG 导出合并为同一次渲染，删除第二次全相机渲染；
- 删除用最终 stage 编号作为除数的错误 `time_per_stage_seconds`，改为记录真实阶段数、影像数、geometry 和 online 每影像耗时；
- 增加地图准备、语义排队、语义等待、RGB/Semantic TDOM、checkpoint、CUDA allocated/reserved/peak 等阶段级计时。

414 个逐相机 masked PSNR 的均值与最终聚合 PSNR 误差小于 `4e-15`。

### 2.5 多进程存在忙轮询

数据预处理和训练协调曾使用 `Queue.empty(): continue`。这既持续占用 CPU，也不是可靠的并发同步方式。现在改为阻塞式或带超时的 `Queue.get()`；需要检测故障的位置在超时后检查子进程存活状态。

### 2.6 默认输出包含无用的大文件和模糊目录

旧版默认生成约 592 MB 的 `model/training_state.pt`，但其 phase 为 `run_complete`，恢复逻辑不会把它当作合法阶段 checkpoint。输出还混有 `qa`、`Intermediate_Results` 和无意义编号目录。

现在：

- 默认不保存 checkpoint；需要恢复能力时显式使用 `--recovery_checkpoint_every_stages`；
- 默认不保存最终调试训练状态；需要时显式使用 `--save_final_training_state`；
- 正式目录收敛为 `model/`、`products/maps/`、`renders/cameras/`、`videos/`、`metrics/`、`logs/` 和 `provenance/`；
- 成功后清理 `.work/`；
- 完整输出从 1,461,265,441 bytes 降至 890,692,167 bytes，减少 39.05%。

### 2.7 训练过程视频未有效利用画布

旧视频固定为 3840×1080。Phantom3 最终地图是纵向场景，两幅约 784 px 宽的地图分别在两个超宽面板内居中，中间产生 1124 px 黑色间隔，主体区域约 62% 为黑色。

新布局把 3840 作为最大宽度，根据最终全局地图宽高比生成内容适配画布：

- RGB TDOM 与 Semantic TDOM 共享尺度并固定间隔 24 px；
- 图例位于语义地图右侧独立栏，不遮挡地图；
- 类别色块和文字沿地图高度展开；
- 保持统一世界网格、逐渐扩大的观测窗口、黑色未观测区和最终 `exact_final` 帧。

stage 14–18 真实预览输出为 2366×1080，主体黑色比例约 31%，地图间距为 24 px。按照完整 Phantom3 的地图比例，未来完整视频预计约为 1974×1080，而不是固定 3840×1080。

## 3. 每张影像训练速度是否提升

### 3.1 同口径全量对比

| 指标 | 修复前全量 | 修复后全量 | 变化 |
|---|---:|---:|---:|
| `geometry_seconds_per_image` | 2.791 s | 2.823 s | +1.13%，基本持平 |
| `online_seconds_per_image` | 3.963 s | 3.179 s | -19.80% |
| `ProgressiveTrain` | 1116.525 s | 1129.116 s | +1.13% |
| `ProgressiveEndToEnd` | 1585.291 s | 1271.417 s | -19.80% |
| 全程墙钟时间 | 2374.792 s | 2014.231 s | -15.18% |

`ProgressiveTrain` / geometry 基本没有变快，因为本轮没有减少训练迭代、模型容量或 Gaussian 数量。优化集中在训练外围但用户实际必须等待的语义同步、视频生成、重复渲染和输出阶段。

### 3.2 与 2.4 秒的关系

2.4 秒通常来自较早、较小的场景阶段或不同统计范围。Gaussian 数、累计相机数和可见性工作集会随阶段增长，因此应使用相同 stage 范围、模型状态和计时边界比较。

- 完整 stage 14–414：2.823 秒/影像，比 2.4 秒慢 17.62%；
- 小范围 stage 14–18：约 2.23–2.26 秒/影像，比 2.4 秒快约 5.8%–7.1%；
- 同口径全量新旧比较：2.823 对 2.791 秒，纯几何没有提升。

结论是：不能把小范围早期结果外推为全量每影像速度。当前可确认的收益是完整在线流程吞吐提升，而不是几何 kernel 本体提速。

## 4. 最终训练效果是否提升

### 4.1 RGB 重建指标

| 指标 | 修复前 | 修复后 | 趋势 |
|---|---:|---:|---|
| L1 | 0.01836001 | 0.01830371 | 降低 0.31% |
| PSNR | 31.05586279 dB | 31.07439446 dB | 增加 0.01853 dB |
| SSIM | 0.89031692 | 0.89079155 | 增加 0.000475 |
| LPIPS | 0.26773250 | 0.26681690 | 降低 0.34% |
| Gaussian 数 | 680557 | 680884 | 增加 327 |

四个指标方向均略好，但幅度很小。它们说明修复没有造成可见的 RGB 质量回归，也可能存在轻微改善；由于两次训练可能存在 GPU 调度和浮点执行差异，不能把这点变化归因于性能修复，更不能称为显著质量提升。

### 4.2 语义结果

最终结果满足：

- `semantic_status=exact_final`；
- `publication_status=complete`；
- `semantic_through_image=000414`；
- lag 为 0；
- deferred 和 errors 为空；
- 最终语义状态由冻结几何上的 414 张有效标签完整重建。

本轮加速有意降低了在线近似状态与最终精确状态的一致程度：`online_class_agreement` 从 0.9046 降到 0.8637，mean JS divergence 从 0.0255 升到 0.0452。这是避免在线全历史重放后预期的中间状态权衡，不影响最终 `exact_final` 重建，但意味着不能把在线预览当作最终权威地图。

当前没有独立语义真值集或 mIoU、per-class IoU、F1 等指标，因此不能断言最终语义精度提高。可确认的是：最终语义证据完整、状态诚实、RGB/Semantic 地图空间对齐，且最终发布过程没有错误。

## 6. 仍值得继续优化的部分

最终精确语义重建耗时 204.714 秒，其中投影耗时 190.872 秒。这是冻结最终几何后保证权威结果的必要 O(images × visible geometry) 工作，不能用在线近似替代。后续可评估：

- 缓存相机可见性和固定投影信息；
- 对标签读取和投影做批量流水；
- 缓存同一次运行中不会变化的 COLMAP 相机与点 ID 索引；
- 只传输增量相机状态，避免阶段级累计结构重复构造；
- 在等价性测试约束下优化 CUDA 投影分块。

这些优化必须保持最终语义 state、地图网格、支持域和发布 manifest 的一致性，不能通过减少训练量或降低模型容量伪装成等价提速。

## 7. 2026-09-21：240 帧、1 FPS 全量视频验收

本轮使用 Phantom3 的完整 stage 14–414 验证以下折中设置：

```text
--training_progress_target_frames 240
--training_progress_fps 1
```

最终成功运行位于：

```text
/data3/xzp/data/Onthefly/phantom3/outputs/runs/phantom3-v2-progress240-fps1_20260921-180740_c886ce6
```

生成的视频为 H.264、1958×1080、1 FPS、240 帧，总时长 240 秒。时间采样覆盖初始化、238 个在线阶段和最终精确重建，stage 间隔主要为 1–2 张影像；它不是把视频编码帧率误当成训练采样频率。

完整训练结果为 677723 个 Gaussian、86000 次累计优化迭代，RGB 指标为 L1 0.018358、PSNR 31.0578 dB、SSIM 0.890348、LPIPS 0.267047。最终语义状态为 `exact_final`，覆盖全部 414 个相机，lag 为 0，deferred 与 errors 均为空。

本轮暴露并修复了两个与视频参数无关的问题：

- 首次运行因公共 `/dev/shm` 已使用约 183/189 GiB，进程间队列分配触发 SIGBUS。第二次运行在私有 mount namespace 中挂载 32 GiB tmpfs 作为 `/dev/shm`，完整训练成功；这避免清理或干扰其他用户的共享内存。
- progressive trainer 使用 `persistent_union` 训练和评估 414 个相机，但最终 stage 的局部 COLMAP 快照只有 27 个相机，旧逻辑会把这份局部 `cameras.json` 当成最终模型清单。现在最终保存前直接从 trainer 的累计相机状态原子写入完整清单，并拒绝重复相机 identity。历史局部清单保存在 `provenance/final_stage_local_cameras.json` 供审计。

最终验收包括 414 个逐相机 RGB/semantic render、所有发布文件 SHA-256 一致性、视频首/中/末帧目视检查，以及完整测试集 233 项通过。运行没有保存 checkpoint 或最终训练状态，临时 `.work` 已在成功发布后清理，`outputs/latest` 已指向该结果。
