## 1. 问题边界

本文记录 UAVScenes AMtown01 全量渐进训练中已经实际出现的耗时长尾和显存峰值，目的是为后续性能优化建立可复现的问题基线。本文不是优化已经完成的声明，也不改变当前训练的算法、数据或产物契约。

观测运行目录：

```text
/data3/xzp/data/UAVScenes_Onthefly/interval5_AMtown01/outputs/runs/amtown01-v2-output-v2_20260917-142222_ac275d0
```

运行启用了 13–487 阶段渐进训练、100 万高斯预算、持久并集语义、最终逐相机渲染，以及 120 帧 RGB TDOM + Semantic TDOM 训练过程视频。视频地图使用发布地图 8 倍的固定 GSD，并要求每个采样边界语义 lag 为 0。

## 2. 已观测事实

### 2.1 普通视频采样帧约需 28–37 秒

训练早期和稳定阶段，相邻视频帧元数据的落盘间隔大多为 28–37 秒。这个间隔包含两帧之间的增量训练、语义同步和地图渲染，不能直接等同于单个渲染函数耗时；当前日志粒度还不足以把三部分完全拆开。

### 2.2 语义状态恢复附近出现数分钟长尾

阶段 142 和 146 对应的视频帧落盘间隔分别约为 404 秒和 413 秒。长尾发生在在线语义经历 `stale_online`、历史证据陈旧并随后恢复的区间附近。运行期间语义边界最终能达到 lag=0，且没有报告语义错误。

这说明长尾与语义历史证据恢复存在明显相关性，但在补充细粒度计时之前，不能断言全部时间都由语义恢复单独造成。

### 2.3 输入稀疏点云文件本身并不大

曾将慢阶段概括为“大点云预处理”，该表述不够准确。实际检查 138–152 阶段：

- `points3D.bin` 约为 145–250 KB；
- `images.bin` 约为 2.0–5.8 MB；
- 单阶段 `GaussianSplatting/<stage>` 目录约为 5.9–16 MB。

因此，不能把数分钟长尾归因于原始稀疏点云文件体积。真正随训练增长的是累计相机状态、高斯状态、可见性/掩膜关系、地图覆盖范围和持久语义证据。

### 2.4 显存存在高峰，但当前没有泄漏证据

训练子进程常态显存约为 6–8 GiB；数据预处理所在主进程另持有约 510 MiB CUDA 上下文。已观察到约 17–19 GiB 的瞬时总峰值，随后在阶段切换后回落到约 5–7 GiB。当前设备容量为 24 GiB，尚未发生 OOM。

显存能够回落，说明目前更像是地图/语义恢复或阶段合并的临时工作集与 CUDA 缓存峰值，而不是单调增长的显存泄漏。仍需通过每进程的 allocated/reserved/max 指标验证这一判断。

### 2.5 数据预处理进程存在忙轮询

`DataPreProccesser.run()` 中多处采用以下模式：

```python
if queue.empty():
    continue
```

这会在没有消息时持续占用 CPU，而且 `multiprocessing.Queue.empty()` 本身不适合作为可靠的并发同步原语。它不一定是阶段长尾的主因，但属于确定存在、可以低风险消除的资源浪费。

### 2.6 每阶段存在可避免的重复构造候选

当前数据路径会按阶段重新读取 COLMAP 相机和稀疏对应数据，建立点 ID 到坐标/颜色的映射，并重新堆叠累计相机矩阵。单次数据量不大，但 475 个阶段重复执行后会形成可观的累计开销和内存分配压力。

## 3. 为什么预处理仍然必要

COLMAP 的稀疏重建不能直接作为新增高斯的完整初始化。每个新影像至少需要：

1. 读取相机位姿、内参和稀疏 2D–3D 对应；
2. 通过有效区域掩膜排除无效或去畸变后不可用像素；
3. 在 2D Delaunay 三角形内采样；
4. 用重心坐标插值得到新增 3D 点及颜色；
5. 将增量点、相机和累计高斯状态交给训练器。

优化目标应是消除重复工作、降低峰值并使同步增量化，而不是删除这些保证几何一致性的步骤。

## 4. 第一性原理下的优化优先级

### P0：先补可归因的性能观测

对每阶段分别记录：

- COLMAP 读取与解析；
- 掩膜筛选、三角采样和 2D→3D 插值；
- 相机状态堆叠与跨进程传输；
- 增量训练；
- 语义排队、更新、历史恢复和等待 lag=0；
- RGB TDOM 与 Semantic TDOM 的逐瓦片渲染；
- 视频帧合成与写盘；
- 各进程 CUDA allocated/reserved/max 和主机 RSS。

没有这些拆分计时，就只能看到帧间总延迟，无法证明具体优化的收益。

### P1：用阻塞队列替换忙轮询

将 `queue.empty(): continue` 改为带短超时的 `Queue.get(timeout=...)`，超时后执行子进程健康检查。目标是降低空闲 CPU 占用，同时保持故障可检测性。该改动不应改变数值结果。

### P1：让语义历史恢复真正增量化

持久并集策略遇到不完整 overlap snapshot 时会正确拒绝不完整证据，但恢复路径不应重放超出必要范围的历史。候选方案是保存每相机或每证据组的充分统计，并依据几何版本只重投影受影响部分。

必须维持以下正确性约束：

- 不完整快照不能被当成完整历史；
- 视频采样帧仍要求 RGB 与语义处于同一阶段边界；
- `stale_online` 必须如实保留，不能通过改状态名称隐藏；
- 最终产物仍必须执行 exact-final 语义重建。

### P1：缓存固定 COLMAP 数据并只传输增量相机状态

`GaussianSplatting/<stage>` 是固定输入，可以按文件哈希缓存解析后的只读结构。点 ID 索引、相机标定和不会变化的影像元数据不应在同一次运行中重复构建。跨进程消息应优先传新增或变更相机，累计状态由接收端维护。

缓存必须绑定源文件哈希、预处理参数、相机模型和代码版本，避免错误复用。

### P2：瓦片级增量地图渲染

当前视频已经使用 8 倍较粗 GSD，Semantic TDOM 已按 256 行分块。下一步可让 RGB TDOM 同样严格分块，并根据新增相机视锥、变化高斯包围盒和语义变更范围，只重渲染受影响瓦片；未变化瓦片从上一帧复用。

增长画布、固定原点/坐标轴/GSD、黑色未观测区域和全场景视图契约必须保持不变。

### P2：减少预处理 CUDA 上下文与临时分配

当前 2D→3D 插值硬编码使用 CUDA，即使图像数据设备配置为 CPU。应基于实测比较：

- CPU 向量化插值，消除预处理 CUDA 上下文；
- 单一 GPU 进程内复用缓冲区；
- 继续使用 GPU，但显式限制临时块大小并记录峰值。

因为输入稀疏点规模较小，CPU 向量化有可能以很小的时间代价换取更低显存，但必须通过基准测试确认。

### P3：训练状态本身的显存优化

100 万高斯的属性、梯度和优化器状态是基础显存成本。可评估可见高斯子集训练、混合精度状态和更紧凑的优化器表示，但这些改动可能改变数值轨迹，风险高于前述工程优化。

直接降低 `GaussiansNumMax` 会改变模型容量和最终质量，不应被包装成等价的性能优化。

## 5. 建议的验收方法

优化应至少比较同一数据、随机状态和参数下的以下指标：

- 全程墙钟时间及 P50/P95/P99 阶段耗时；
- 语义恢复阶段的最大等待时间；
- GPU 峰值 allocated/reserved 和每进程显存；
- 主机峰值 RSS 与空闲期 CPU；
- 最终高斯数量、RGB 指标、语义状态和产物哈希/结构；
- 120 帧视频的帧数、阶段边界、lag、画布对齐和视觉一致性。

低风险优化应做到结果契约完全不变；涉及浮点执行顺序或模型容量的优化，需要单独定义允许的数值误差和质量回归阈值。

## 6. 当前结论

当前最值得优先解决的不是原始点云文件大小，而是：缺少细粒度剖面、语义历史恢复长尾、队列忙轮询、每阶段重复解析/累计状态构造，以及地图渲染未充分复用。应先完成观测和不改变数值语义的优化，再评估训练状态压缩等高风险方案。

## 7. 2026-09-17 阶段 259 显存失败与修复

首次全量视频运行在阶段 259 主动失败。错误不是随机 CUDA OOM，而是 Semantic TDOM 的容量保护：

```text
Semantic TDOM fixed working set is 340046560 bytes,
but the byte budget or CUDA capacity after headroom is 23068672 bytes
```

失败前物理 GPU 显存约为 23.45/24.56 GiB。根因是训练过程视频的 RGB TDOM 仍使用整幅 rasterizer；随着场景和 Gaussian–tile 相交数量增长，它产生的大型临时 binning 工作集被 CUDA allocator 缓存。RGB 图已经复制到主机后，这些可回收缓存仍影响紧随其后的语义容量判断，导致语义固定工作集无法保留 512 MiB 安全余量。

修复保持地图数值契约不变：

- 训练过程视频的 RGB TDOM 改用项目已有的精确水平分条 renderer；
- 每个 RGB stripe 完成后立即复制到 CPU；
- RGB 完成并转为 `uint8` 后，在语义 TDOM 开始前显式释放 CUDA allocator cache；
- Semantic TDOM 在测量可用容量前也释放可回收缓存；
- 语义完成后再次释放临时缓存，避免影响下一训练阶段。

分条 RGB renderer 已有与整幅参考逐像素一致的 CUDA 集成测试。本次新增测试还要求训练视频路径必须调用分条 renderer、不得回退到整幅 renderer，并验证 RGB 与语义之间的 cache release 边界。

### 小范围验收

按生产参数 `semantic_tdom_render_tile_rows=256` 在阶段 13–17 做了完整 smoke：

- 5 个渐进阶段和 final refinement 全部完成；
- 最终语义状态为 `exact_final`，publication complete；
- 视频为 H.264、3840×1080、4 FPS、3 帧；
- 首帧为阶段 13 initialization，末帧为阶段 17 final refinement；
- 所有视频帧语义 lag 为 0；
- 运行成功后 `.work` 被清理。

测试专用的 `render_tile_rows=16` 在真实阶段 13 数据上曾触发 semantic CUDA kernel 非法访问；生产配置 256 未复现。该 16 行边界问题应作为独立 CUDA 内核问题处理，不应通过降低生产 tile 大小规避显存问题。

## 8. 后续训练策略

从本记录起，代码或参数变化后的训练验证先使用小范围阶段子集；默认使用阶段 13–17，并包含 initialization、至少一个 progressive 边界、final refinement、最终语义发布和视频编码。只有小范围测试、完整单元测试和相关 CUDA 集成测试均通过，且用户另行确认后，才启动 13–487 全量训练。
